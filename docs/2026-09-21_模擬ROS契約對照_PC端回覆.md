## 11. 實作：P0/P1 修正（2026-09-21 完成）

### TF 權責決策 —— 方案 A

Isaac **一條 TF 都不發**，全部交給與實車同一套節點：

```
map            → odom             ndt_localizer
odom           → base_footprint   odom_drift_injector (publish_tf:=true)
base_footprint → base_link        robot_state_publisher（URDF 0.13）
base_link      → velodyne_link    robot_state_publisher（URDF −0.02, 0, 1.3）
```

理由：TF 數字全部來自實車 URDF，論文可主張模擬與實車共用同一份運動學描述。
代價是必須把模擬感測器的**實體位置**搬到與 URDF 一致（已由 `align_sensor_prims_to_urdf()` 處理）。

### 過程中修正的兩個自身錯誤（測試抓到）

1. **row-vector 慣例**：`pxr` 是 `p' = p × M`。原本寫 `rotMatrix * offset`（column-vector）
   等同乘上轉置＝反向旋轉，x 算成 `−0.03196`，正解 `+0.00374`，**差 3.6 cm** ——
   比原本要修的 4.2 cm 誤差還大。改用矩陣合成 `velo_to_base * base_xf`。
2. **錨點選錯**：原本錨定 `base_link`，殘留 3.66 mm（USD 的 `base_footprint→base_link`
   是 0.1336 而非 URDF 的 0.13）。正解是錨定 **`base_footprint`** ——
   因為 `IsaacComputeOdometry` 的 `chassisPrim` 就是它，TF 樹的 `odom→base_footprint`
   對應的實體是那顆 prim。

兩者都是「驗結果不驗算式」的測試抓到的：測試直接量 stage 上的 `base_footprint→velodyne`，
而不是檢查有沒有呼叫某個函式。

### 附帶查證

- `chassis_imu` 的 timeStamp **原本就正確**接在 `isaac_read_simulation_time`，

## 14. 第 3 件事：點雲掃描運動拖影（完成）

### 模型

靜止世界點 W 在 t 時刻被測得（感測器位姿 S(t)），記錄 `p_t = S(t)⁻¹·W`；
但整包被標成 t_end 的時戳，消費端誤以為世界位置是 `S(t_end)·p_t`。
由理想快照 `p_end = S(t_end)⁻¹·W` 反推真實失真點：

```
p_smear = Δ · p_end,   Δ = S(t)⁻¹·S(t_end)
        = R(ω·dt)·p_end + v·dt,     dt = t_end − t
        
dt = T_scan · (1 − ((φ − φ₀) mod 2π) / 2π),   φ = atan2(y, x)
```

dt 由方位角決定 —— 這正是拖影的來源。

### 管線分層（與 odom 一致）

```
Isaac /velodyne_points_ideal  ──lidar_motion_smear──▶  /velodyne_points  ──▶ NDT / policy
Isaac /odom_gt                ──odom_drift_injector─▶  /odom             ──▶ NDT / policy
```

拖影吃 `/odom_gt`（**真值**速度）而非 `/odom`，因為畸變由真實運動造成。

### 測試驗證的物理量

| 測項 | 期望 | 出處 |
|---|---|---|
| 0.8 m/s × 100 ms 最大位移 | **8.0 cm** | 車端 2026-08-24 實測 |
| φ=0（掃描起點） | dt = T_scan，位移最大 | — |
| φ=π（正後方） | dt = T_scan/2，該牆當時近 4 cm | — |
| 純轉向 ω=1.0，10 m 處 | 2·r·sin(ω·T/2) 弧長 | 走廊轉角最大畸變源 |
| 靜止 | 位移恆為 0 | 驗收表 20 倍判準的前提 |

### ⚠ 已知限制（論文須誠實陳述）

本節點對**單一快照做幾何扭曲**，重現的是點位移（主效應，8 cm 量級）。
真實掃描中不同方位是從不同位置量測的，因此還有視差與遮蔽變化 ——
這部分無法由單一快照還原，屬二階效應（牆面在 5–20 m 時可忽略）。

完全物理正確的做法是改用 **RTX Lidar 旋轉掃描模式**，但代價是
RTX Lidar 不對骨架網格行人做光線追蹤（論文 §2.8.2 已載明），行人會照不到。
本專案選擇「PhysX Lidar + 確定性拖影注入」，與 `odom_drift_injector` 採
確定性 UMBmark 模型的方法論一致（皆為可重現的 A/B 對照）。

## 20. 效能：真正的瓶頸是 headless 的渲染解析度

| 設定 | RTF | 點雲頻率 |
|---|---|---|
| 初始（1280×720，每步渲染） | **0.028** | 0.3 Hz |
| 關掉另一個 Isaac GUI | 0.033 | — |
| render_every=6 | 0.121 | 2.9 Hz |
| **128×128 + render_every=6** | **3.801** | — |
| 128×128 + render_every=2 | 0.98（已節流） | 6.7 Hz |
| **128×128 + render_every=1 + 實時節流** | **0.89** | **10.1 Hz** ✓ |

**關鍵是解析度**：headless 下沒有任何東西需要那些像素（PhysX Lidar 走 raycast，
也沒有 camera 在發布），但 `SimulationApp` 預設仍以 1280×720 在算。壓到 128×128 後快了 **31 倍**。

⚠ **渲染不能完全關掉**：`render_every=0` 會讓整張 Action Graph 停擺 ——
`OnPlaybackTick` 綁在 app update / render tick 上，不是物理步。
實測現象是 `/velodyne_points_ideal` 從 topic list 消失，`/clock` 與 `/odom_gt` 一則訊息都不發。

壓到 128×128 後反而比實時快 3.8 倍，所以加了**實時節流**（`--free-run` 可關閉）——
policy 的推論迴圈是照牆鐘跑的，模擬若比實時快，每個模擬秒拿到的決策次數就少於實車。

## 22. 定位精度定案 + 拖影 A/B（2026-09-21）

### ⭐ odom frame 慣例：車體對齊（不是世界對齊）

先前兩度判斷錯誤，最後用**直接觀測**定案：車直行時

```
odom_raw = (+9.242, -0.129) → (+14.600, -0.160)
           odom.x 單獨增加，odom.y 幾乎不變
```

⇒ `IsaacComputeOdometry` 的 odom frame 與**車體起始朝向**對齊。
真值換算必須是：

```python
world = start_world + R(start_world_yaw) @ (odom.x, odom.y)
map   = world_to_map(world)
```

我先前「確認世界對齊」那次，是被前幾輪測試殘留的位移污染了 ——
**在髒狀態下做的判斷不可信**，這是本次最大的方法論教訓。

### NDT 追蹤精度（直行 0.25 m/s）

| 臂 | 位置誤差中位 | 最大 |
|---|---|---|
| 拖影 OFF | **0.288 m** | 0.316 m |
| 拖影 ON | **0.268 m** | 0.307 m |

兩臂**無顯著差異**，而且誤差在整段行程中幾乎是常數（不是發散）——
代表這 0.27 m 是**系統性偏移**而非追蹤失敗，來源應是 World↔map 配準的殘差
（手刻走廊 vs 實掃點雲，10 cm 解析度下重疊率 0.86）。

### 拖影在目前速度下低於雜訊底

車端的「8 cm 畸變」是 **0.8 m/s** 下的數字。模擬目前 `speed_rate=0.35`
→ 實際上限 0.35 m/s，測試用 0.25 m/s，畸變只有 **2.5 cm**，
低於 NDT 的定位雜訊底（0.27 m），所以 A/B 量不出差別。

**要驗證拖影的效果必須把速度拉到 0.8 m/s 量級**，否則這項 sim-to-real 注入
在論文裡無法宣稱有可觀測影響。

### ⚠ A/B 實驗設計：每一臂都要連 Isaac 一起重啟

第一次 A/B 無效：只重啟 ROS 棧、沒重啟 Isaac，車還在 28 m 外，
但 `sim_initial_pose` 又餵了一次 c28 → NDT 被種子拉回原點後就找不到車，
誤差 29 m。**這不是拖影造成的**。

## 26. RViz 點雲閃爍 transform 錯誤（2026-09-21 使用者回報）

### 症狀與根因

【感測】光達原始點雲 velodyne 與濾波後點雲 filtered 間歇性顯示 transform 錯誤。

實測時戳關係：

```
velodyne_points      最新 = 188.000
odom→base_footprint  最新 = 188.000   ✓ 同步
map→odom (NDT)       最新 = 187.900   ← 落後 100 ms（剛好一個 NDT 週期）
```

RViz 的 Fixed Frame 是 `map`，要把 t=188.000 的點雲畫出來就需要該時刻的 `map→odom`，
但最新只到 187.900 → `Lookup would require extrapolation into the future`。

**這是結構性的**：NDT 必須先收到第 N 幀點雲、算完才能發出對應 TF，
那時第 N+1 幀已經出來。有時趕上、有時沒有，所以是**閃爍**而非持續錯誤。

為什麼只有 RViz 受影響：policy 查 TF 用 `rclpy.time.Time()`（最新可用），
RViz 的 PointCloud2 display 用**點雲的精確時戳**。

### 修正：`ndt.cpp` 加 `transform_tolerance`

`ndt.cpp:594` 原本是 `transform_stamped.header.stamp = pose_msg.header.stamp;`，
**沒有任何容差**。AMCL / slam_toolbox 等標準定位節點都有這個機制。

新增 `transform_tolerance` 參數（**預設 0.0 = 車端原行為完全不變**），
`sim_deploy.launch.py` 設 0.1。**只延長 TF 的有效時間窗，不動任何定位運算。**

驗證：

| | 點雲最新時戳 | map→odom 最新時戳 | 關係 |
|---|---|---|---|
| 修正前 | 188.000 | 187.900 | 落後 100 ms ✘ |
| 修正後 | 296.600 | 296.700 | **領先 100 ms** ✓ |

已記入 `sim_ws/patches/README.md` 第 2 項。
